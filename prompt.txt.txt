AI Traffic Model Evaluation - Test Suite Implementation
Objective
Create a comprehensive testing framework to evaluate the performance of our AI traffic control model against a baseline (fixed-timing traffic lights) using SUMO (Simulation of Urban MObility).
Critical Requirements
File Organization
ALL test-related files MUST be placed inside a tests/ folder at the project root. This includes:

Test runner scripts
Test scenario configurations
Metrics extraction modules
Statistical analysis modules
Output/results files
Generated reports and visualizations
Any helper utilities, fixtures, or mocks
README and documentation for the test suite

Do NOT scatter test files across the project. Everything related to testing lives under tests/.
Suggested structure:
tests/
├── README.md
├── config/                  # YAML/JSON configs for traffic levels & scenarios
├── scenarios/               # Scenario definitions (low/med/high traffic)
├── runners/                 # Scripts that execute SUMO simulations
├── metrics/                 # Metric extraction & aggregation modules
├── analysis/                # Statistical comparison & significance testing
├── reports/                 # Generated output: CSVs, charts, summary reports
├── outputs/                 # Raw SUMO XML outputs per run
└── utils/                   # Shared helpers, seed management, etc.
Full Determinism / Reproducibility (NO RANDOMNESS)
Tests MUST be 100% reproducible. Running the same test twice MUST produce byte-identical metric outputs. Enforce this strictly:

Fixed SUMO seed — pass --seed <fixed_int> to every SUMO invocation (and --random false)
Fixed Python RNG seeds — random.seed(), numpy.random.seed(), and any framework-specific RNGs (PyTorch, TensorFlow) must be seeded with constants
AI model determinism — if the model uses neural networks, set deterministic flags (torch.use_deterministic_algorithms(True), torch.backends.cudnn.deterministic = True, tf.config.experimental.enable_op_determinism()), and disable dropout/sampling at inference time
Fixed vehicle routes and departures — pre-generate route files (.rou.xml) once with a fixed seed, then reuse them; do NOT regenerate routes at runtime
Hash-check output files — include a sanity test that runs the same scenario twice and asserts metric outputs are identical
No wall-clock dependencies — never use time.time() or datetime.now() as inputs to any logic that affects the simulation
Pin library versions — include a requirements.txt with exact versions in tests/
Set PYTHONHASHSEED=0 in the test environment

Since runs are deterministic, a single run per configuration is sufficient — no need for multi-seed averaging. However, the test suite should still log the seed used so anyone can verify reproducibility.
Test Architecture
Test Type 1: Comparative Performance Testing (Same Scenario, Variable Traffic)
Run identical map configurations under three traffic load conditions:

Low traffic — ~30% of network capacity
Medium traffic — ~60% of network capacity
High traffic — ~90%+ of network capacity

For each traffic level, run two parallel simulations:

Control: Existing SUMO map with fixed-timing traffic lights (current configuration)
Experimental: Same SUMO map with our AI model controlling the lights

Metrics to Implement and Compare
Each metric below must have its own dedicated test module inside tests/metrics/ and produce a comparable number for both the baseline and the AI run. All metrics are derived from SUMO's standard output files (tripinfo.xml, summary.xml, emissions.xml, queue.xml, statistics.xml) — no need to estimate anything manually.
Primary Metrics

Average travel time — mean time from vehicle spawn to network exit (from tripinfo.xml)
Estimated CO₂ emissions — total and per-vehicle (from tripinfo.xml emission attributes, HBEFA model)

Required Additional Metrics (one test module per metric)

Average waiting time at junctions — mean time vehicles spend with speed < 0.1 m/s while approaching/at junctions. Use SUMO's waitingTime attribute from tripinfo.xml, and optionally cross-check via TraCI per-junction polling.
Average queue length per junction — mean number of halted vehicles per intersection over the simulation duration. Configure SUMO with --queue-output <file> and aggregate from the resulting XML.
Throughput — total vehicles that completed their routes per simulation hour. Count entries in tripinfo.xml and normalize by simulated duration.
Average network speed — mean vehicle speed across all vehicles and timesteps. Available from summary.xml (meanSpeed attribute) or aggregated via TraCI.
Number of teleports — count of SUMO teleport events (gridlock recovery). Available from summary.xml (teleports attribute) and the simulation log. Lower = better.
Time loss — difference between actual and ideal (free-flow) travel time. Direct attribute timeLoss in tripinfo.xml.
Fuel consumption — total liters consumed across all vehicles. Attribute fuel_abs (or equivalent) in tripinfo.xml emissions output.
Pollutant emissions breakdown — separate totals and per-vehicle averages for NOx, PMx, HC, and CO. All available from tripinfo.xml when emissions output is enabled with the HBEFA model.
Stops per vehicle — average number of times each vehicle stops (speed drops below 0.1 m/s then recovers). Track via TraCI step-by-step or post-process from FCD output (--fcd-output).
Junction-level fairness — variance (and standard deviation) of waiting times across different approaches at each signalized junction. Group vehicles by the junction approach lane they used, compute mean wait per approach, then compute variance across approaches. Reported per junction and as a network-wide average. This ensures the AI isn't starving any direction to optimize others.

Each metric module should:

Expose a single function like compute_<metric_name>(sumo_output_dir) -> dict
Return both the raw value and any relevant breakdown (per-vehicle, per-junction, etc.)
Be unit-testable in isolation with sample SUMO output files (include small fixtures under tests/utils/fixtures/)

Implementation Requirements
SUMO Invocation
Every simulation run must include these flags to ensure all metrics can be computed:
--seed <FIXED_INT>
--random false
--tripinfo-output tests/outputs/<run_id>/tripinfo.xml
--summary-output tests/outputs/<run_id>/summary.xml
--queue-output tests/outputs/<run_id>/queue.xml
--statistic-output tests/outputs/<run_id>/statistics.xml
--emission-output tests/outputs/<run_id>/emissions.xml
--device.emissions.probability 1.0
--emissions.volumetric-fuel true
Reporting

Generate one master CSV (tests/reports/results.csv) with columns: scenario, traffic_level, controller (baseline|ai), metric, value
Generate a markdown summary report (tests/reports/summary.md) with comparison tables and percentage improvement of AI vs baseline for each metric
Generate visualizations (tests/reports/charts/) as bar charts for each metric across the three traffic levels, baseline vs AI side-by-side
Include a final "verdict" section in the report indicating which metrics the AI improved, which it regressed on, and the overall recommendation

Configuration

Reuse existing SUMO map files as-is for the baseline — do NOT modify them
Traffic-level parameters (insertion rates, vehicle counts) configurable via tests/config/traffic_levels.yaml
All fixed seeds defined in one central file: tests/config/seeds.yaml

Deliverables

Complete tests/ folder following the structure above
